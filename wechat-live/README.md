# wechat-live · 微信实时意图解读浮层

对方发来一条消息，**1 秒内**在旁边弹出一块浮层，告诉你这句话背后是什么意思、
TA 现在什么状态、你该怎么回。

通用聊天分析，不预设关系类型 —— 同事、朋友、家人、对象都能用。

用 **TypeSafe Jev**（System One 决策模型）判定 —— 它不生成文字，只输出带概率的
结构化判定，所以不会像普通 LLM 那样顺着上下文自己编故事。

## 原理

```
Weixin.exe 写入 session.db（加密 + WAL）
      │
      │  每 200ms：比对 mtime，没变就 0 开销跳过
      ▼
   解密 session.db（0.5 MB，约 9 ms）→ 读 SessionTable
      │
      │  目标会话 last_timestamp 变大 = 有新消息
      ▼
   解密 message_0.db（81 MB，约 0.45 s，只在启动时做一次）
   之后靠 WAL 增量 patch 保持最新
      │
      │  按 local_id 游标增量取新消息，用 real_sender_id 判断谁发的
      ▼
   动态静默窗口（0.6 ~ 3.0 s，看结尾标点和已发了几片）
      │
      │  碎片 smart_join 成一条，再写进上下文
      ▼
   按时间断档切段 → 本次对话 + 上次对话，两段都带时间
      │
      ▼
   调 Jev（上次那段要不要算进来，由它判断）→ 浮层渲染
```

**端到端延迟约 1 秒**（含静默等待，实际 1.5~4 秒）。

### 控制条

浮层标题栏右边三个控件：

| 控件 | 作用 |
|---|---|
| `张三 ▾` | 点开换人面板，见下 |
| `⏸` / `▶` | 暂停 / 继续解读。暂停期间消息**照常进上下文**，只是不调 Jev —— 一恢复就能接着用，不用重新预热 |
| `✕` | 退出 |

### 换人：点名字搜就行

```
┌──────────────────────────────────┐
│ [ 输入名字 / 备注 / zs         ] │
│ 已在监听                          │
│   ● 张三                          │
│ 搜索结果                          │
│   李四            lisi001         │
│   王五（同事）     wangwu88        │
│ 回车选第一个 · Esc 关闭            │
└──────────────────────────────────┘
```

输入认这几种写法，都是查 `contact.db`（2.9 MB，整个读进内存，搜一次 1~2 ms）：

| 输入 | 命中 |
|---|---|
| `张三` | 备注名 |
| `zs` | 备注拼音首字母 —— 微信自己维护的字段，白捡 |
| `zhangsan` | 备注全拼 |
| `zhangsan001` | 微信号 |
| `wxid_abcdefghij` | wxid 片段 |
| `小张` | 对方昵称 |

排序按命中精确度：wxid > 备注 > 微信号 > 拼音 > 前缀 > 包含。
公众号和群聊也会列出来，但点不动 —— 现在只支持一对一。

选中后新对象在后台加载（定位消息库 + 预热上下文，实测 0.02 ~ 0.16 s），
加载好自动切过去，标题栏名字就变了。

**原来那个人继续收消息**，只是不再调 Jev；他攒着没解读的碎片会先并进上下文，
所以切回来是连续的，不会缺一段。

> 加了人之后 `config.json` 不用改 —— 里面那个 `targets` 只是**启动时**的初始名单。
> 想启动就自动盯某个人，把他的 wxid 写进去；**留空 `[]` 就是启动后一个人都不盯**，
> 浮层空着等你自己点标题栏挑（默认就是留空）。

微信 4.0 (xwechat) 的库格式要点：

- SQLCipher 4：每页 4096 字节，末尾 80 字节保留区，最后 16 字节是 IV；第 1 页前 16 字节是 salt
- 会话消息表名 = `Msg_` + md5(username)
- 发送者：`real_sender_id` → `Name2Id.rowid` → `user_name`

## 快速开始

```bash
# 前提：微信在跑 + Clash 代理开着（127.0.0.1:7897）

python live.py                # 正式使用
python live.py --dry          # 只打印抓到的新消息，不调 Jev（调链路，不花钱）
python live.py --replay 3     # 把最后 3 条当新消息重放，验证整条链路（约 $0.0003）
```

双击 **`run_live.bat`** 也可以。

**启动后浮层是空的**，标题栏显示「未选 ▾」，谁都不盯。点它 → 搜备注 / 拼音首字母
→ 选中，才开始监听那个人（见下方「换人」）。想启动就自动盯人，把 wxid 写进
`config.json` 的 `targets`。

浮层会自动贴到微信窗口旁边；微信最小化时，它会退到屏幕右上角待命。
拖动浮层标题栏可以手动移动（拖过之后就停止自动跟随）。

## config.json

```json
{
  "targets": [],
  "me": "wxid_你的wxid",
  "db_dir": "C:\\Users\\<用户名>\\Documents\\xwechat_files\\<wxid_xxx>\\db_storage",
  "keys_file": "C:\\path\\to\\wechat-decrypt\\all_keys.json",

  "poll_ms": 200,
  "warmup_count": 100,
  "context_chars": 150,
  "prev_chars": 800,
  "session_gap_s": 7200,
  "interpret_self": false,

  "merge_gap_s": 15.0,
  "silence": {
    "default": 1.5, "end_punct": 0.6, "mid_punct": 2.0, "short": 2.2
  },

  "wechat_window_class": "Qt51514QWindowIcon",
  "overlay": { "side": "right", "offset_x": 14, "width": 400, "alpha": 0.97 }
}
```

| 字段 | 说明 |
|------|------|
| `targets` | 启动时自动盯上的人。**留空 `[]`（默认）就谁也不盯**，开了浮层现选 |
| `targets[].username` | **要盯的 wxid**（不是微信号、不是备注名）。查法见下 |
| `me` | 你自己的 wxid，用来区分消息是谁发的 |
| `poll_ms` | 轮询间隔。文件没变化时只是 stat 调用，200ms 开销极小 |
| `context_chars` | 本次对话给多少**字**（不是条数）。短消息不白占位，长消息不撑爆 |
| `prev_chars` | 上次对话给多少字，比本次多 —— 它多数时候用不上，用上就是关键线索 |
| `session_gap_s` | 隔多久没说话算「上次聊天」。默认 7200 秒 = 2 小时 |
| `interpret_self` | 要不要也解读自己发的消息（默认 false，但自己的消息仍进上下文） |
| `warmup_count` | 启动时预热多少条历史。默认 100 —— 得够往回够到「上次对话」 |
| `merge_gap_s` | 同一人连发的合并间隔。超过这个秒数就算新一轮，不合并 |
| `silence.*` | 动态静默窗口的四个档位，见下 |
| `overlay.width` | 按 96 dpi 的逻辑像素写，程序会按实际 DPI 自动换算 |
| `overlay.side` | `right` 优先贴右边，右边放不下自动翻到左边 |

### 两段上下文

一对一聊天里，新来的一句话可能接两种东西，光看一段上下文分不清：

- 接**几分钟前**的话：「方案改完了吗」→「下午发你」→「别又忘了」
- 接**几天前**的话：上次在挑键盘，今天突然来一句「就那个吧」

所以每次解读给 Jev **两段**，该不该把上次的算进来**由它自己判断**：

| 字段 | 内容 | 默认量 |
|---|---|---|
| `recent_context` | 本次对话（相邻两条间隔 < `session_gap_s`） | 150 字 |
| `previous_conversation` | 上次对话（更早一段，和本次之间隔着断档） | 800 字 |

按**字数**取而不是条数 ——「嗯」「好」按条数取白白占位，一条几百字的倾诉按条数
取又可能把整段撑爆。两段都带说话人和时间，跨天会标成「昨天 22:15」「前天 09:30」，
隔了多久一眼可见。

> 判「那个指哪一次说的」这种事，代码判不准（要解析指代、要理解话题），
> 但语言模型看得出来。所以这里只负责把两段都摆好，判断交给 Jev。

启动和切换对象时能往回读到上次对话，靠的是 `warmup_count` —— 它得够大，
不然上次那段根本不在内存里，切段就切不出来。

### 动态静默窗口

等多久才认定「对方说完了」，取决于最后一片长什么样：

| 档位 | 触发条件 | 默认 |
|---|---|---|
| `end_punct` | 结尾是 `。！？!?…～~` —— 说完了 | 0.6 s |
| `mid_punct` | 结尾是 `，、；：` —— 明显没说完 | 2.0 s |
| `short` | 没有标点、且不超过 5 个字 | 2.2 s |
| `default` | 其他 | 1.5 s |

**已经在分片的话还会再加**：`+0.4 × min(片数-1, 2)`，最多 +0.8 s。
加成要封顶 —— 对方已经发了 5 片，说明节奏就这样，再往上加只会让浮层越来越慢。

碎片合并时会判断中文边界：中文之间直接连（`我` + `觉得` → `我觉得`），
其他情况补空格。库里读出来的历史同样是碎的，预热时走同一套合并。

## 注意事项

**微信新建分片库后要重新提取密钥**（最坑的一个，踩过）。微信把消息按会话分到
`message_0/1/2.db`，并且**隔一阵就新开一个**（用着用着 `message` 目录下
就多出来一个库）。`all_keys.json` 只是**某一次提取的快照** —— 新库没密钥就永远
解不开，之后所有新消息都写进那个库。现象非常像"监听坏了"：进程在跑、日志干净、
目标也切过去了，就是一条消息都不来。

程序启动时会检查，看到这行就说明该重新提取了：

```
[!] 有 1 个消息库没有密钥：message_2.db
```

**双击 `tools\wcdb-key-tool\rekey.bat`**（会自动请求管理员权限，微信要在运行），
跑完重启 `live.py` 即可。

> **别再跑 `python main.py decrypt`** —— 它看到 `all_keys.json` 存在就直接跳过
> （`ensure_keys` 里 `if keys: return`），而且 `decrypt` 那步还有 argparse 冲突，
> 会报 `unrecognized arguments: decrypt` 直接退出。等于是**什么都没干、还报了个错**。
>
> 微信 4.1+ 也不再在内存里明文缓存密钥了：老工具扫的 `x'<hex>'` 模式被 XOR 混淆过，
> 扫不到（实测在 GB 级的内存里一个都没命中）。`wcdb-key-tool` 走的是另一条路 ——
> 定位运行时 `Config.Cipher` 对象 → 解混淆 → **逐库 HMAC 校验**，校验通过才采信。

**只支持文本消息**。图片、语音、表情、文件先跳过（`local_type != 1`）。
对方发这些不会触发解读。

**微信版本**。当前针对微信 4.0（xwechat，`db_storage` 目录结构、Qt 界面）。
微信 3.x 的库结构完全不同，不适用。

**浮层是独立窗口**，不是注入微信的。它靠 `topmost` 浮在最前面 + 跟随微信窗口坐标
来达到「贴在旁边」的视觉效果。所以它也会浮在其他程序上面。

## 踩坑记录

**1. 截断解密会被 SQLite 拒收**
想省时间只解密前几百页来探测表在哪，结果报
`malformed database schema - invalid rootpage` —— SQLite 解析 schema 时会校验
每个表的 rootpage 是否落在文件范围内。后来实测**全量解密 81 MB 只要 0.45 秒**
（瓶颈是磁盘 IO 不是 CPU），根本不用省。顺带一提：多线程反而更慢，GIL 卡住了。

**2. 用时间戳做游标会漏消息**
轮询间隙用 `create_time > 上次` 拉增量，同一分钟内连发的多条消息时间戳完全相同，
会被整批漏掉（实测重放 2 条只抓到 1 条）。改用 `local_id`（表内自增）做游标就稳了。

**3. 用行号当 rowid 会认错人**
`Name2Id` 表没有显式 id 列，一开始用 `enumerate()` 的行号当 rowid 去查发送者，
结果把消息全标成了别人。必须 `SELECT rowid, user_name`。

**4. 高 DPI 屏上文字发虚**
不声明 DPI 感知时，Windows 会把窗口位图整体拉伸到实际 DPI（125% 屏就是放大 1.25 倍），
字明显糊。要在 `Tk()` 之前调 `SetProcessDpiAwareness`，然后把 config 里的宽度
按 DPI 换算成物理像素。注意声明之后 `win32gui` 返回的坐标也变成物理像素 ——
两边必须一起切，否则浮层会贴错位置。

**5. 浮层高度被初始尺寸压住**
`winfo_reqheight()` 量的是内容自然高度，但如果窗口一开始被 `geometry` 设成小尺寸，
量出来的会被压扁，导致底部内容被裁。解法是先把窗口撑到屏幕高度再量。

**6. 只盯主库 mtime 会漏掉所有新消息**（最隐蔽的一个）
SQLite 在 WAL 模式下写入只改 `-wal`，主库要等 checkpoint（WAL 攒满 4 MB）才更新。
`SessionReader` 一开始只看主库 mtime，等于新消息根本触发不了检测 —— 现象是
「程序在跑但永远不响」，偶尔才莫名其妙反应一次。实测排查时发现主库 mtime
比库里最新消息的时间戳**滞后了 43 分钟**。
修法：stamp 里把 `-wal` 一起算上，解密主库后再补一次 `patch_wal`。
`MessageStore` 一开始就带了 WAL，`SessionReader` 漏了 —— 同一个坑写了两遍只填了一半。

**7. 提示词里「别把上文算进来」会让 Jev 直接无视上下文**
`_ONLY_TARGET` 原本写的是「recent_context 仅作背景参考……**不要把它的问题算到
target_message 头上**」。本意是防止 Jev 把上一条的旧账算到当前这条头上，
实际效果是它连指代都不解析了 —— 拿一句「就那个」给它，它不知道「那个」指什么。
**否定的措辞要小心：模型分不清"别用上文做结论"和"别用上文"。**
改成正面说明上下文该怎么用（判断这一条在回应什么、代词指向谁、隔了多久、
现在处在什么关系状态），只在最后收一句「结论只描述这一条」。
同一个坑在 `recent_context` 上还有第二层：**上下文必须带时间戳**。
「对方隔了三天才回一句」和「隔了三十秒」，是完全不同的两件事。

**8. 一个消息库被多个会话共用时的两个坑**
微信把消息按会话分片，但 `message_0.db`（80 MB）装着大部分聊天 —— 所以一旦
盯上两三个人，他们多半落在同一个库里。这时候：

- `locate()` 原本「没找到目标表就把解密副本删掉」。听起来合理，其实会误删
  别的会话正在用的那份 80 MB 副本，害得人家下次得重解一遍。之所以一直没炸，
  纯粹是因为 Windows 的文件锁挡下了删除（`OSError` 被 `except` 吞了）。
  改成**只删这次自己新解的**，复用来的不动。
- 主库被 checkpoint 改写时，副本作废、必须全量重解。但每个共用这个库的会话
  都会各自发现一次，于是解了 N 遍 80 MB。加了一个进程级记录
  `_full_decrypted[库路径] = 主库版本`，第一个发现的负责解，其余的复用。
  版本号用**主库 mtime** 而不是副本文件的 mtime —— 副本 mtime 会被每次
  `patch_wal` 刷新，拿它做判断容易被时钟精度骗过去。

**9. 同一个会话的表在好几个分片库里都有**
微信按会话分片，但**同一个会话的表可以在多个库里同时存在** —— 新库建好之后
老表并不删，只是冻结不再写入。实测某个人的表：`message_0.db` 里二十几条（停在更早的日期）、
`message_1.db` 里十几条、`message_2.db` 里六十条（还在涨）。

`locate()` 原本是「按文件大小降序，第一个命中就返回」，于是永远停在 80 MB 的
`message_0.db` 上 —— 新消息全在新库里，一条都看不见。现象是「切过去一个人，
浮层毫无反应」，跟「监听坏了」长得一模一样，白查了半天。

改成**在含目标表的库里挑消息最新的那个**（比各库中该表的 `MAX(create_time)`）。
代价是每个候选库都要解开看一眼，102 MB 首次约 1 秒，之后走缓存
（实测 0.03~0.05 s）。缓存文件本来就按库名分开（`message_0.dec.db` /
`message_2.dec.db`），所以每个库只需要解一次，切来切去都是复用。

**10. 「只看这一条」把最直接的前文也一起排除了**
`_flush()` 判定一批消息的最后一条时，上下文取的是**这批之前**的 `ctx_n` 条
（`cut = len(tg.ctx) - len(merged)`），等于把同批里排在目标前面的那几条整个
排除掉了。

但一批通常就是一轮完整对话 ——「对方问 → 我答 → 对方又问」。判定最后那个
「对方又问」时，「我答」反而不在上下文里。极端情况（对方一口气连发三条、中间
没有我的消息）下上文直接是**空的**，Jev 拿着一句话凭空判断它在回应什么。

改成定位目标在 `tg.ctx` 里的下标、往前取 `ctx_n` 条。实测同一批三条的场景：
修复前上文 `[]`，修复后 `['方案改完了吗', '下午发你']`。

这个坑和 7 是一对：**7 是提示词里告诉模型「别用上文」，10 是根本没把上文给它。**
两个都修完之后判定才真正开始用上下文。
