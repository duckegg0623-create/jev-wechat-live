# jev-chat · 聊天记录意图解读工具

用 **TypeSafe Jev**（System One 决策模型）解读聊天记录：一条一条判定对方消息的**情绪**、
**语气**、**真实意图**、**该怎么回**，再聚合成一份**关系氛围报告**。

Jev 不生成文字，只输出带概率的结构化判定（是/否、分类、打分），所以判词不会像 LLM 那样
自己编故事——这是它相对普通大模型解读的核心优势。

> ⚠️ **这是个没做完的实验项目。** Jev 在「读懂言外之意」这类任务上准确率不达标，
> 我们没能解决这个问题。失败现象、11 条真实消息的逐条对照、A/B 实验数据、
> 以及我们对原因的判断，全在 [`../KNOWN_ISSUES.md`](../KNOWN_ISSUES.md)。

## 快速开始

```bash
# 0. 填配置：复制 config.example.json 成 config.json，填 openrouter_api_key
#    走代理的话把 proxy 改成自己的端口（不需要代理就填 ""）

# 1. 解析聊天记录（从 QQ/微信 直接复制粘贴到 txt）
python parse_chat.py "D:/path/to/聊天记录.txt"

# 2. 逐条判定（全量；约 0.4 秒/条，100 条约 $0.01）
python jev_client.py

# 3. 聚合成报告
python aggregate.py --me "你的昵称"

# 或者：即时解读单条消息（日常最常用）
python jev_read.py "所以呢？" -c "方案改完了吗|我今天下午发你"
```

双击 **`run.bat`** 可直接进入交互模式，连续输入对方的消息看解读。

## 文件说明

| 文件 | 作用 |
|------|------|
| `jev_client.py` | Jev API 客户端 + 氛围分析 9 项问题集 + 批量跑（**核心库**） |
| `parse_chat.py` | 解析 QQ/微信 复制的聊天记录纯文本 → `data/parsed.jsonl` |
| `aggregate.py` | 把逐条判定聚合成关系氛围报告（话轮合并、回应力度、温度曲线等） |
| `jev_read.py` | **即时解读**：给一条消息，出「对方在想什么 / 我该怎么回」 |
| `demo_on_chat.py` | 用真实记录里的典型消息批量演示解读效果 |
| `config.example.json` | 配置模板。**复制成 `config.json` 再填自己的 key** |
| `run.bat` | 双击启动交互式解读 |

数据文件都在 `data/` 下：

| 文件 | 内容 |
|------|------|
| `parsed.jsonl` | 解析后的逐条消息（speaker / time / text） |
| `jev_results.jsonl` | 每条消息的 9 项 Jev 判定原始结果 |
| `分析报告.txt` | 聚合后的关系氛围报告 |

## config.json

```json
{
  "openrouter_api_key": "sk-or-v1-...",
  "proxy": "http://127.0.0.1:7897",
  "endpoint": "https://openrouter.ai/api/alpha/decisions",
  "model": "~typesafe/jev-latest",
  "context_n": 6,
  "workers": 8
}
```

- **`openrouter_api_key`**：必填，去 <https://openrouter.ai/keys> 申请。缺了会直接退出
- **`proxy`**：必须与本地代理端口一致，连不上时先查这里（不需要代理就填 `""`）
- **`endpoint`**：OpenRouter 的 decisions 端点。**只有这一个**，别再加 fallback ——
  曾经配过一个 `/api/v1/api/alpha/decisions`，`/api` 重复，永远 404，唯一作用是
  把前一个端点的真实错误（比如上游 503）覆盖成 404，让人以为是路径写错了
- **`context_n`**：每条消息附带前 N 条作上下文。**上下文对判定影响极大**（实测同一条
  「所以呢？」，带不带上下文结论完全不同），但对成本是线性增加

## 输入格式

从 QQ / 微信 里框选聊天记录复制，粘贴成 txt 即可。识别格式是「昵称 + 时间 + 内容」三行一组：

```
小明
2024年01月01日  12:00
今天几点碰头

大雨
2024年01月01日  12:02
六点半吧
```

解析器以**时间行**为锚点定位，所以对空白行波动、多行消息、格式小差异都不敏感。

## 成本

实测（`typesafe/jev-1.13-20260917`）：

- 单条消息 9 项判定：**$0.0001**，延迟约 0.76 秒
- 全量跑几百条（含 6 条上下文）：19.4 秒，**$0.032**
- 即时解读单条（7 项）：**$0.0006**

## 两个问题集

### 氛围分析（`jev_client.py`，9 项）

批量跑全量记录用：积极率、敷衍倾向、回避倾向、主动抛话、延续话题（5 个是/否）
+ 情绪、意图（2 个分类）+ 情绪强度、投入程度（2 个打分）。

### 即时解读（`jev_read.py`，7 项）

单条消息实时用：

| 判定 | 类型 | 输出 |
|------|------|------|
| `literal_same` | 是/否 | 字面说的和真正想表达的，是同一件事吗 |
| `emotion` | 分类 8 | 情绪状态（平静 / 开心 / 烦躁 / 低落 / 兴奋 / 敷衍 / 困惑 / 认真） |
| `tone` | 打分 5 | 语气亲疏（冷淡生分 ↔ 热络亲密） |
| `real_intent` | 分类 8 | 真实意图（问信息 / 求助 / 分享告知 / 吐槽 / 开玩笑 / 约时间 / 闲聊 / 给反馈不满） |
| `relationship` | 分类 4 | 关系状态（轻松聊天 / 正常 / 有点拘谨 / 明显不对劲） |
| `need` | 分类 6 | 对方期待（要答案 / 要方案 / 要倾听 / 要表态 / 要陪同 / 不需要什么） |
| `best_action` | 分类 8 | 怎么回（直接答 / 追问澄清 / 给方案 / 接情绪 / 开玩笑 / 婉拒 / 先不接 / 先查证） |

> **这套选项不够用，实测判定准确率明显低于预期** —— 原因分析、11 条真实消息的
> 逐条对照结果、A/B 实验数据都在 [`../KNOWN_ISSUES.md`](../KNOWN_ISSUES.md)。
> 发出来的是个**半成品**，我们没能解决这个问题，希望有人能接手。

## 踩坑记录

**上下文污染**：Jev 会把 `recent_context` 里的情绪算到 `target_message` 头上。
原作者实测：一句无害的「Как дела」跟在脏话后面，profanity 被判 0.75。
所以两个问题集里都加了显式的隔离措辞：

> 只评估 target_message 这条消息本身。recent_context 只是背景上下文，
> 不要把它的内容或情绪算到 target_message 头上。

**碎片化连发会让统计失真**：有人习惯把一句话拆成多条发（「我」「觉得」「这样不行」
分三条发出来，拼起来才是一句完整的话）。
按**单条**统计回应力度，会得出「对方比你主动得多」这种完全相反的结论——
因为对方抛完话题马上又发下一条，根本没给对面插话的窗口。
`aggregate.py` 的 `build_turns()` 按**话轮**（同一说话人 30 分钟内连续消息合并）统计，
修正后结论反转成「互动基本对等」。**看报告时留意这一节。**

**OpenRouter 模型列表里查不到 Jev**：`/api/v1/models` 里没有它（走的是独立的
Decisions 端点，不是 chat completions）。所以 Cherry Studio、OpenWebUI 这类
「填 model id」的客户端大概率调不动，只能走本工具的代码路径。
